# 2026 W46（11-09 ~ 11-15）· 历史列表分页 + 测试进仓库

## 做了什么

首页的历史列表不再「一次扫 300 条 span 再分组」，改成**按运行分页**：一页 20 次运行，先分页，再取每棵树。

`notes/2026-W43.md` 的「下一步」第 2 条 —— 唯一一处「数据量一大就会坏」的地方 —— 做完了。

## 想清楚的事

### 1. 这不是性能问题，是静默的正确性问题

一开始记的是「扫 300 条太慢」。真正写的时候才看清：慢是次要的，**结果是错的**。

一次 agent 运行有 6–9 个 span。`take: 300` 是按 span 截断的，窗口边界很容易落在某次运行中间：

```
第 300 条 ──┐
            ├─ llm_call（在窗口里，parentId 指向窗口外的 agent_run）
第 301 条 ──┘  tool_call（在窗口外，没查进来）
```

`buildTree` 会把没有父节点的 span 当成新的根 —— 页面不报错，只是那次的树少了几层。这种错**不会有人发现**，因为没人知道自己「本来该看到什么」。

所以分页的单位必须是「运行」，不能是「span」。这个问题在 25 次运行的规模下看不出来，但只要开始用就一定踩。

### 2. 两次查询，而不是一次

```ts
// 第一步：只拿 runId，分页在这里发生
prisma.span.groupBy({
  by: ['runId'],
  _max: { createdAt: true },
  orderBy: [{ _max: { createdAt: 'desc' } }, { runId: 'asc' }],
  skip, take: RUNS_PER_PAGE + 1,
})

// 第二步：把这 20 次运行的 span 全部取回来（刻意不设 take）
prisma.span.findMany({ where: { runId: { in: runIds } } })
```

为什么不一条 SQL 做完：一次运行该取多少条 span，取决于这次运行自己 —— 在 SQL 里表达就是窗口函数（`row_number() over (partition by runId)`），Prisma 不支持，得写裸 SQL。两次查询各自走索引，代价是两次往返，换来的是**不用为了一个分页去维护一段裸 SQL**。

第一次查询多取一条，用来判断有没有下一页，省掉一次 `count`。

### 3. 为什么是页码，不是游标

游标分页（「给我比这个时间更早的」）在时间撞车时会漏数据：两次运行的最后一个 span 落在同一毫秒，`<` 会把其中一次跳过。运行数量少、翻页不频繁，`skip/take` 的缺点（翻页时刚好有新数据写入可能重复或跳过一条）相对可以接受。

严格的做法是复合游标 `(createdAt, runId)`，但 `groupBy` 的 `having` 里做字段间比较很难写对，收益也不大。**知道代价、写进 README，比装作没有好。**

## 测试进仓库

`npm test` 跑 36 个纯函数用例，用的是 Node 自带的 test runner + `tsx`，**没有新增依赖**。

### 为什么不再装一套 Vitest

被测的都是纯函数：不需要 mock 模块、不需要渲染组件、不需要快照。为了断言一个字符串解析结果引入一个 bundler，收益不抵成本。`tsx` 本来就在依赖里（之前跑临时脚本用的），`tsx --test` 直接认 tsconfig 的 `@/` 别名。

**等哪天要测 React 组件或需要 mock 模块，再换也不迟。** 工具应该跟着需求长，不是提前占位。

### 集成测试为什么不进 `npm test`

它们会真调模型、真写库、真花钱。放进 `tests/integration/` 手动跑，而且脚本默认只允许 localhost —— **一个 `npm test` 不该能悄悄改掉线上数据**。要打远端得显式 `ALLOW_REMOTE=1`。

## CI

测试有了，但只有自己想起来才跑；而 `main` 一推就自动发生产。两者之间没有关卡 —— 改错一行 push 上去，线上就是坏的。

`.github/workflows/ci.yml` 补上这道关卡：push 到 `main` 或提 PR 时，GitHub Actions 依次跑

```
npm ci → npx tsc --noEmit → npm run lint → npm test
```

第一次跑 59 秒，全绿。**不用配任何 secret**——单测是纯函数，`prisma generate` 只读 schema、不连库。workflow 里那两个 `POSTGRES_*` 是假值，只是让 generate 不抱怨变量缺失。

### 一个没想到的坑：workflow 文件要额外权限

```
refusing to allow an OAuth App to create or update workflow `.github/workflows/ci.yml`
without `workflow` scope
```

`gh` 默认 token 只有 `repo` / `read:org` / `gist`，而 GitHub 规定**修改 `.github/workflows/` 下的文件要有 `workflow` 权限**——防止有人偷改别人的 CI 去跑恶意脚本。

修法：`gh auth refresh -s workflow --hostname github.com`。注意 `gh` 不走 git 的代理配置，国内直连 OAuth 接口会超时，得自己带 `HTTPS_PROXY=http://127.0.0.1:7897`。

### 为什么先在分支上验证

推 `main` 会连带发生产，而 CI 能不能跑通还不确定。所以把提交推到 `ci/github-actions` 分支、开 PR——`pull_request` 事件照样触发 CI，生产不受影响。**验证通过再合进 main**，顺序反过来就是拿生产当试验场。

## 已知欠账

- CI 只覆盖纯函数单测；集成测试仍然要手动跑（见 `tests/integration/README.md`）
- 集成测试要先手动起服务、跑完还要手动清理；可以再包一层脚本，但它是低频操作，先这样
- React 组件没有测试（需要渲染环境，是另一类工具）
- `/api/runs` 的 GET 仍在按 span 返回（`limit` 上限 200），目前没有前端在用，先不动
- 读数是**本页汇总**，不是全部历史汇总 —— 标签已改成「本页运行」，但页面上还没写一句说明
- 历史的 `?page=N` 是普通链接，不是客户端翻页，每次翻页会整页重新渲染（可以接受）
