# 2026 W42（10-12 ~ 10-18）· Stage 0 完成并上线

## 做了什么

Stage 0：单次 LLM 调用的记录本。能发 prompt 给 DeepSeek，把 token / 耗时 / 输入输出落库，页面上能看到历史记录和成本估算。

## 踩到的坑（都值得记，因为全是「不报错但结果错」那一类）

### 1. DeepSeek 的模型别名下线了

`deepseek-chat` 和 `deepseek-reasoner` 这两个名字 **2026-07-24 就下线了**。现在只有 `deepseek-flash` 和 `deepseek-v4-pro`。

**为什么坑**：网上几乎所有教程（包括中文的）还在写 `deepseek-chat`。照抄不会编译报错，只在运行时返回 400。我是直接打 API 的 `/models` 端点问出来的，没敢照抄教程。

**以后怎么办**：接新 provider 时，先打一次它的 `/models` 端点看实际有哪些模型，别信文档和教程。

### 2. AI SDK 7 的 usage 字段是嵌套的

拿 token 数不是：

```ts
result.usage.reasoningTokens          // ❌ undefined，不报错
```

而是：

```ts
result.usage.outputTokenDetails.reasoningTokens   // ✅
```

`inputTokens` / `outputTokens` 在顶层，但**细节字段都收进了 `outputTokenDetails` 和 `inputTokenDetails`**。输入侧还有 `inputTokenDetails.cacheReadTokens`（命中缓存的 token，价格便宜几十倍）。

**为什么坑**：TypeScript 会拦住写成顶层的情况（这次就是 tsc 帮我抓到的）。但如果用 `any` 或者 JS，就会静默存一堆 null 进数据库，页面上显示 0 token，你还以为是模型没返回。

**教训**：涉及第三方 SDK 的字段，**不要凭记忆写，去读 `node_modules` 里的 `.d.ts`**。我这次就是靠 `grep` 类型定义确认的。

### 3. thinking 开着的时候，temperature 完全失效

DeepSeek V4 **默认就开 thinking**。而 thinking 开启时，`temperature` 和 `topP` 会被**静默忽略**。

**为什么坑**：用户拖温度滑块，没反应，会以为是自己的代码坏了。实际是模型根本不看这个参数。

**怎么处理的**：界面上开启思考模式时，直接把温度输入框**禁用**并写明原因。宁可让它明显不可用，也不要让它「看起来能用但实际被忽略」。

这条其实是个通用的产品原则：**不要给用户一个不起作用的控件**。

### 4. Next 16 默认开了 Cache Components（这个是意外收获）

写了 `export const dynamic = 'force-dynamic'` 结果直接 500：

```
Route segment config "dynamic" is not compatible with `nextConfig.cacheComponents`.
```

Next 16 的新模型是：**默认预渲染静态外壳**，遇到「未缓存数据」（比如我的 Prisma 查询）就报错，要求你显式处理。框架给了三条路：

| 方案 | 做法 | 适用 |
|---|---|---|
| stream | 用 `<Suspense>` 包住 | ✅ 我选的 |
| cache | `"use cache"` | 数据不常变时 |
| block | `export const instant = false` | 整页必须等数据 |

**我选了 stream**：页头和表单不依赖数据库，立刻可见，能马上开始输入；记录部分流式补上。构建产物里 `/` 标的是 `◐ Partial Prerender`——静态外壳 + 动态流式内容。

这比原来的 `force-dynamic`（整页等服务端查完库）体验更好，而且这是框架想让你走的路线。

## 一个技术选型的取舍：Prisma 6 而不是 7

Prisma 7 是当前版，但做了破坏性改动：必须用 driver adapter、必须有 `prisma.config.ts`、且**不再自动读 `.env`**。网上教程 90% 还是 6 的写法。

**选了 6**，理由是现阶段「能对上教程、少一层配置」比「用最新版」更重要。

**代价要知道**：Prisma 7 的 driver adapter 正是为 Serverless 准备的方向。以后要部署到 Vercel 时，可能得重新面对这个升级。

### 5. Serverless 存不住本地文件 —— 推迟躲不掉的问题

Vercel 的函数跑在**临时容器**里：请求来了开一个，处理完就扔。往容器里的 SQLite 文件写数据，下一个请求落到别的容器就找不到了。

**所以「本地跑得好好的」和「线上能存住」是两回事。**

解决办法是把数据库换成**网络数据库**（Neon Postgres）——连接串走网络，跟容器生死无关。

代价是换库要改 schema 的 provider + 重新生成迁移文件。因为 Stage 0 刻意没用 SQLite 独有类型（`input` / `output` 用 String 存 JSON 而不是 Json 类型），改动很小。**那个准备没白做。**

### 6. Neon 为什么给两个连接串

| 变量 | 主机名特征 | 用途 |
|---|---|---|
| `POSTGRES_PRISMA_URL` | **带** `-pooler` | 应用连库 |
| `POSTGRES_URL_NON_POOLING` | **不带** | 跑迁移 |

**应用为什么要用连接池**：Serverless 每个请求可能开一个新进程、每个进程一条连接。不池化的话，几百个请求就能把 Neon 免费版的连接数打满。

**迁移为什么不能用连接池**：连接池是 pgbouncer，它只做转发，不支持迁移要用的部分 SQL（如 advisory lock），走它迁移会随机失败。

**记住特征就行**：主机名里有没有 `-pooler`。写反了线上直接连不上。

### 7. 数据库报错时，Next 回了「空响应体的 500」

`prisma.span.create()` 原来写在 `try/catch` **外面**。数据库一出错，异常直接抛给 Next，Next 回一个**没有 body 的 500**，前端只看到 `Unexpected end of JSON input` —— 完全查不出原因。

**修法**：写库单独包一层，失败时返回带 `error` 字段的 JSON。

**顺带一个业务判断**：模型调用可能成功了、但记录没落库。这种情况**绝不能返回 `ok: true`** —— 前端会以为存下来了，实际丢了一次调用数据。所以错误信息写成「调用成功，但记录写入数据库失败」，把两件事分开说。

### 8. 环境变量改了不会自动生效

Vercel 改环境变量**不会**触发重新部署，必须手动 Redeploy（或推一个 commit）。否则改完以为好了，线上跑的还是旧值。

### 9. 凭据卫生：这次真踩到了

操作时我把 Neon 的数据库密码**贴进了对话**。密码一进聊天记录就等于公开 —— 会被传到服务器、可能被缓存。

**规则：变量名可以发，值不可以。** 凡是 `password` / `key` / `secret` / `token` 后面跟着的那串字符，不要贴进任何对话框、聊天窗口或截图。

**泄露了怎么办**：立刻去源头**轮换**，再把用到它的地方全部更新。这次的做法：

1. Neon 控制台 Reset password
2. Vercel CLI 更新线上变量
3. 改本地 `.env`
4. 重新部署 + 验证

**轮换时的两个细节**：
- Vercel CLI 没有「原地修改环境变量」，只能 `vercel env rm` 再 `vercel env add`
- 值要**走 stdin，不要走命令行参数** —— 命令行参数会出现在系统进程列表里，等于又公开一次

### 10. gitignore 是「后面的规则覆盖前面的」

`vercel link` 自动往 `.gitignore` 末尾追加了 `.env*`，把第 3 行的 `!.env.example` **盖掉了** —— 放行规则失效。

**记住**：`!` 开头的放行规则必须写在**忽略规则后面**才有效。

### 11. Git Bash 在 Windows 上的两个坑

- **内联的中文参数会乱码**。`curl -d '{"prompt":"中文"}'` 传过去变成 `��һ��`。
  解法：**把内容写进文件，用 `--data-binary @文件`**，别走命令行参数。
- **`/tmp` 不是同一个 `/tmp`**。Git Bash 的 `/tmp` 是它模拟的，Node 不认，会报
  `ENOENT: no such file or directory, open 'D:\tmp\resp.json'`。**统一用绝对路径。**

### 12. `gh` 装了不等于 git 能用它

`gh auth login` 只让 `gh` 自己登录了，`git push` 还是不知道用什么凭据（报 `could not read Username`）。
要跑一次 **`gh auth setup-git`**，它把 gh 注册成 git 的 credential helper。**这一步没人会主动告诉你。**

### 13. 收尾：变量类型 + 清理

**`DEEPSEEK_API_KEY` 从 Config 改成 Secret。** Config 类型的值对项目成员可见，控制台会标
「Needs Attention」。Secret 是**只写不读** —— 建完连控制台和 CLI 都读不出值，只能覆盖。

**删掉 6 个带失效旧密码的变量。** Neon 集成注入了 8 个含密码的变量，只有 2 个被应用读取。
剩下 6 个（`DATABASE_URL` / `POSTGRES_PASSWORD` / `PGPASSWORD` / `POSTGRES_URL` /
`POSTGRES_URL_NO_SSL` / `DATABASE_URL_UNPOOLED`）留着的坏处**不是「密码泄露」**（那密码已经作废了），
而是**陷阱**：以后哪个工具按惯例去找 `DATABASE_URL`，会拿到一个连不上的值，报的是认证失败 ——
而不是「变量不存在」。后者一眼就懂，前者要查半天。**宁可没有，也不要有个错的。**

**学到一条**：`vercel env` 有 **`update`** 子命令，能原地改值、还能 `--sensitive` 改类型。
我轮换密码时用的是「先 `rm` 再 `add`」，其实没必要冒那个险（万一 add 失败，变量就没了）。

- ~~**6 个带旧密码的 Vercel 变量**~~ —— **10-17 清掉了**，见上面第 13 条。
- ~~**`DEEPSEEK_API_KEY` 不是 Secret 类型**~~ —— **10-17 改成 Secret 了**，见上面第 13 条。
- **思考模式的 token 没单独存**。`output_tokens` 里已经包含了思考消耗的 token，但没拆出来。
  想显示「输出 1240（其中思考 1100）」需要给 span 表加一列。CLAUDE.md 说「后续只加字段，不推翻」，加这一列是符合约定的，只是 Stage 0 没做。
- **每次写库都 `await`，会挡住流的消费**。`for await (const event of ...)` 里每来一个事件就写一次库，
  写库期间不再读流。span 少的时候无所谓，多了会拖慢 agent。
  而且它**污染了工具的耗时测量**：两个工具并行时，后返回的那个把「等前一个写库」的时间也算进去了
  （实测纯算术的 `max` 报了 1560ms，另一个只 550ms）。
  正解是写库和读流解耦（队列 + 收尾时 flush），但要处理好顺序和收尾，Stage 1 不值得。
  **线上那次没触发**（工具耗时 54ms / 8ms，看着很干净），但那只是没撞上并行窗口 —— **不算修好**。
  真要评测时这个数字会变成「评测指标」，必须先修。
- **历史列表是一次扫 300 条 span 再分组**。数据量上来后，分页边界可能把一次运行从中间截断
  （树有孤儿兜底，不会崩，但会少几个节点）。真要分页应该按 runId 分页。
- **`query_spans` 会查到当前正在跑的这次运行**（见第 21 条）。做评测前得决定要不要排除自己。

## 下一步（Stage 2）

`CLAUDE.md` 里的验收标准：**数据集批量跑 + LLM-as-judge 打分 + 两个 prompt 版本对比**。

Stage 1 已经把地基铺好了，从哪下手：

| 现在有什么 | Stage 2 要变成什么 |
|---|---|
| 一次运行 = 一条 prompt，人工点按钮 | 一个**数据集**（一批输入），一键全跑完 |
| 没有打分，只看 token 和耗时 | **LLM-as-judge**：拿模型给模型的输出打分 |
| `system` 提示词是表单里手填的一个框 | 提示词存成**版本**，能对比 v1 / v2 的效果 |

**要新建的**：数据集表、评分表、对比页面。`Span` 表**不用动** —— 评测跑出来的东西本来就是
一次 agent 运行，直接复用现有的 trace 表。这是 Stage 1 把「运行」抽象干净的回报。

**设计上要先想清楚的一件事**：评测是「同一条输入 × 多个 prompt 版本 × 多次重复」的笛卡尔积，
很容易一次跑出几百次调用。得先想好怎么组织（谁是谁的父节点、怎么标识「第几次重复」），
而不是跑起来再说。CLAUDE.md 的「后续只加字段，不推翻」在这里同样适用。

## Stage 1 完成（10-18）

多步 Agent + trace 树 + SSE 流式。**表结构一行没改** —— 只往 `type` 那一列加了个新值 `agent_run`。

验收实测（一次真实运行）：

```
agent_run  Agent 运行         3664 / 187 tok   9.40 s
├─ llm_call  第 1 步            846 /  61 tok   4.94 s
│  └─ tool_call  query_spans        —          3.51 s
├─ llm_call  第 2 步           1367 /  58 tok   1.09 s
│  └─ tool_call  calculate          —          0.27 s
└─ llm_call  第 3 步           1451 /  68 tok   0.79 s
```

线上实测（同一个问题，跑在 Vercel 上）：

```
agent_run  Agent 运行         4200 / 276 tok   3.79 s   ← 流中出现于 +29ms
├─ llm_call  第 1 步            846 /  43 tok   0.68 s
│  └─ tool_call  query_spans        —          0.05 s
├─ llm_call  第 2 步           1588 / 152 tok   1.03 s
│  └─ tool_call  calculate          —          0.01 s
└─ llm_call  第 3 步           1766 /  81 tok   0.71 s
```

**注意「流中出现于 +29ms」这一列**：根 span 在 29 毫秒就到达浏览器了，而整趟跑完要 3.8 秒。
这就是「流式」和「假流式」的分界线 —— 如果是攒完再一起发，这一列会等于总耗时。
服务端和客户端隔着 Vercel 的 serverless 函数，这个数字仍然成立，说明 SSE 没有被中间层缓冲。

**顺带解决了一个上次的疑点**：本地测出来的工具耗时是 1560ms / 550ms（纯算术的工具居然要 1.5 秒），
当时判断是「写库 `await` 挡住了读流，把等待时间算进了工具耗时」。线上这次是 54ms / 8ms —— 干净了。
原因大概是线上两个工具没并行，没撞上那个窗口。**问题还在，只是这次没触发**，不能算修好了。

### 14. 改了 `.env` 必须重启 dev server（这个坑伪装成了网络问题）

本地起服务，报：

```
Can't reach database server at `...-pooler...neon.tech:5432`
```

看着像网络问题。查了一圈：DNS 解析正常、TCP 能连、TLS 握手成功、拿同一个连接串单独跑脚本**能连上**。

**最后发现原因**：那个 dev server 是**轮换密码之前**起的，进程里揣着旧密码。`P1001 连不上` 是 pgbouncer 遇到坏凭据时的表现，不是网络断。

**教训**：环境变量是进程启动时读进内存的，热更新不会重读。**改完 `.env` 重启服务**，这是第一条该做的，而不是最后一条。

**排查方法值得记**：把「应用报错」和「同一个凭据用脚本单独连」放在一起对比 —— 一个失败一个成功，差异就只剩**进程本身**了。

### 15. AI SDK 7 的坑（接着上次的清单）

| 写错 | 正确 |
|---|---|
| `maxSteps: 5` | `stopWhen: stepCountIs(5)` —— `maxSteps` 这个参数已经删了 |
| `tool({ parameters })` | `tool({ inputSchema })` |
| `result.fullStream` | `result.stream` |
| `part.delta`（流式增量正文） | `part.text` |
| 工具抛异常走 `tool-result` | 是独立事件 `tool-error` |

**又一次印证了上次的教训**：这些字段名写错**不报错，静默失效**。我是靠读 `node_modules/ai/dist/index.d.ts` 确认的，不是凭记忆。TypeScript 只能抓到一部分（比如 `parameters` 会被抓），像 `part.delta` 这种拿到 `undefined` 的它抓不到 —— 所以我专门写了个脚本，把真实抓包的流**按 1 字节一块、3 字节一块、随机切块**喂给解码器，看结果是否一致。

### 16. SSE 解码器：末尾那个孤零零的 `\r` 不能立刻处理

自己写的 SSE 解码器在「一次性喂完」的测试里全对，但用 **CRLF 换行**的抓包一测就挂 —— 9 条消息 JSON 解析失败。

原因：CRLF 归一化时，如果 `\r` 恰好是这一块的最后一个字符，它的 `\n` 在下一块开头。分块处理会把 `\r` 当换行吃掉，等 `\n` 到了就多出一个空行，**事件边界整个错位**。

修法：末尾的 `\r` 先扣着不动，等下一块到了再一起判断。

**为什么能发现**：测的时候不是「喂一遍看结果对不对」，而是**同一份数据用不同的切块方式喂 8 遍，结果必须完全一致**。网络一次给多少字节本来就不确定，只测一种切法等于没测。

### 17. 模型一轮可以调多个工具，结果会交错回来

第 2 步里模型**同时**调了 `calculate(average)` 和 `calculate(max)`。两个 `tool_call` 挨着来，两个 `tool_result` 却按各自耗时先后返回。

所以配对**只能用 SDK 给的 `toolCallId`**。按工具名配（同名就串）、按到达顺序配（一并行就错位）都会翻车。

### 18. 工具失败也要记录 —— 而且模型会自己纠正

故意让模型用 `query_spans(limit: 999)` 触发校验失败。结果：

1. 错误被完整记进那条 `tool_call` span 的 `output.error`
2. **模型在第 2 步自己纠正了**：「limit 传 999 被拒了：参数校验规定最大 50，所以没拿到任何记录……要我按上限 50 取一批吗？」

这说明「失败也记录」不只是存档 —— 它是 agent 能自我修复的前提。

### 19. 不能让模型算数

`calculate` 工具存在**唯一**的理由：LLM 是在「猜下一个 token」，不是在做算术。三位数加减都可能错，而且错得很自信。

正确做法不是「让它算准点」，是**别让它算**：模型负责决定「算什么」，精确执行交给工具。提示词里也直接写死了这条规则 —— 不写的话它会很乐意心算。

**同一个思路的另一面**：`calculate` 刻意**不用 `eval`**。eval 会把模型生成的字符串当代码执行，模型一旦被提示注入诱导，就等于把服务器交出去了。

### 20. `aria-expanded` 展开按钮 > `role="treeitem"`

一开始给树的每一行挂了 `role="treeitem"`，ESLint 报「缺少 `aria-selected`」。

本来加个 `aria-selected={false}` 就消警了 —— 但那是在骗人。**ARIA 的 `tree` 角色是有配套义务的**：要 `aria-selected`、要方向键导航、要 roving tabindex。只挂 role 不实现这些，读屏软件会按树的规则念，键盘却操作不了，**比不挂这个 role 更糟**。

改成普通的展开按钮（`<button aria-expanded>`），这是浏览器和读屏都原生支持的模式，够用且不会说谎。

### 21. 一个有意思的副作用：agent 会查到自己的 trace

问「最近 5 次调用平均耗时」，`query_spans` 返回的数据里**包含了这次运行自己刚建的那几条 span**（耗时为 null）。模型发现了，并且如实说了「有一条 latencyMs 为 null，没法纳入计算」。

数据是诚实的，行为也是对的 —— 但这个自指会让「最近 N 次」的统计口径变模糊。真要做评测时得想清楚：查历史数据要不要排除当前正在跑的这次运行。

### 22. 本地和线上连的是同一个库，但还是有「本地不行线上行」

这次真的遇到了一次反向的：本地连不上连接池，线上（Vercel）好好的。原因不是环境差异，是**本地进程里的凭据过期**（见第 14 条）。

**记一条方法论**：报错信息说的是「连不上」，但那只是现象。真正要问的是「哪个环节不同」。这次的成功路径和失败路径之间，唯一的差异是**进程**。
