## 踩到的坑（都值得记，因为全是「不报错但结果错」那一类）

### 1. DeepSeek 的模型别名下线了

`deepseek-chat` 和 `deepseek-reasoner` 这两个名字 **2026-07-24 就下线了**。现在只有 `deepseek-flash` 和 `deepseek-v4-pro`。

**为什么坑**：网上几乎所有教程（包括中文的）还在写 `deepseek-chat`。照抄不会编译报错，只在运行时返回 400。我是直接打 API 的 `/models` 端点问出来的，没敢照抄教程。

**以后怎么办**：接新 provider 时，先打一次它的 `/models` 端点看实际有哪些模型，别信文档和教程。

### 2. AI SDK 7 的 usage 字段是嵌套的

拿 token 数不是：

```ts
result.usage.reasoningTokens          // ❌ undefined，不报错
```

而是：

```ts
result.usage.outputTokenDetails.reasoningTokens   // ✅
```

`inputTokens` / `outputTokens` 在顶层，但**细节字段都收进了 `outputTokenDetails` 和 `inputTokenDetails`**。输入侧还有 `inputTokenDetails.cacheReadTokens`（命中缓存的 token，价格便宜几十倍）。

**为什么坑**：TypeScript 会拦住写成顶层的情况（这次就是 tsc 帮我抓到的）。但如果用 `any` 或者 JS，就会静默存一堆 null 进数据库，页面上显示 0 token，你还以为是模型没返回。

**教训**：涉及第三方 SDK 的字段，**不要凭记忆写，去读 `node_modules` 里的 `.d.ts`**。我这次就是靠 `grep` 类型定义确认的。

### 3. thinking 开着的时候，temperature 完全失效

DeepSeek V4 **默认就开 thinking**。而 thinking 开启时，`temperature` 和 `topP` 会被**静默忽略**。

**为什么坑**：用户拖温度滑块，没反应，会以为是自己的代码坏了。实际是模型根本不看这个参数。

**怎么处理的**：界面上开启思考模式时，直接把温度输入框**禁用**并写明原因。宁可让它明显不可用，也不要让它「看起来能用但实际被忽略」。

这条其实是个通用的产品原则：**不要给用户一个不起作用的控件**。

### 4. Next 16 默认开了 Cache Components（这个是意外收获）

写了 `export const dynamic = 'force-dynamic'` 结果直接 500：

```
Route segment config "dynamic" is not compatible with `nextConfig.cacheComponents`.
```

Next 16 的新模型是：**默认预渲染静态外壳**，遇到「未缓存数据」（比如我的 Prisma 查询）就报错，要求你显式处理。框架给了三条路：

| 方案 | 做法 | 适用 |
|---|---|---|
| stream | 用 `<Suspense>` 包住 | ✅ 我选的 |
| cache | `"use cache"` | 数据不常变时 |
| block | `export const instant = false` | 整页必须等数据 |

**我选了 stream**：页头和表单不依赖数据库，立刻可见，能马上开始输入；记录部分流式补上。构建产物里 `/` 标的是 `◐ Partial Prerender`——静态外壳 + 动态流式内容。

这比原来的 `force-dynamic`（整页等服务端查完库）体验更好，而且这是框架想让你走的路线。

## 一个技术选型的取舍：Prisma 6 而不是 7

Prisma 7 是当前版，但做了破坏性改动：必须用 driver adapter、必须有 `prisma.config.ts`、且**不再自动读 `.env`**。网上教程 90% 还是 6 的写法。

**选了 6**，理由是现阶段「能对上教程、少一层配置」比「用最新版」更重要。

**代价要知道**：Prisma 7 的 driver adapter 正是为 Serverless 准备的方向。以后要部署到 Vercel 时，可能得重新面对这个升级。
