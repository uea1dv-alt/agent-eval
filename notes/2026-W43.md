## 想清楚的事

### 1. 评测的调用为什么不写 Span 表

第一直觉是「评测跑出来的本来就是一次运行，直接复用 trace 表多省事」。但有两处会**静默地把结果做错**：

**token 会串账。** `groupByRun` 把同一个 `runId` 下所有 `llm_call` 的 token 加起来。judge 的调用如果也落成同一次运行的 `llm_call`，**judge 烧的 token 就被算进被测模型的成绩里**。对比页上两个版本的成本差，可能全是判分方式的差 —— 而且不报错。

**首页会被灌满。** 首页只扫 300 条 span 再分组。一次 20 条用例的评测产生 40 条 span，两三次就把列表挤掉了。

结论：**评测是组织层，Span 是执行层。** 不带工具的评测，一条用例就是一次普通调用，本来也没有树可看。

> 这是这个项目里反复出现的同一类判断：先问「这张表代表什么」，再问「方不方便」。方便但语义错的表，会在半年后以「数据看起来不太对」的形式找上门。

### 2. judge 不能是被评模型自己

让模型给自己的输出打分，它系统性地偏爱自己的风格。这不是「可能有点偏差」，是有稳定方向的偏。

所以 `pickJudgeModel(testedModel, preferred)` 里做了**强制兜底**：首选正好是被测模型时，自动从同一 provider 里另挑一个。调用方传什么都不好使 —— 这条约束一旦被绕过不会报错，只会让结论悄悄偏向「自己人」，所以必须写死在代码里，不能靠自觉。

### 3. 解析失败要记 null，不能记 0

judge 的输出是不可控的自然语言。哪怕提示词里写死了「只输出 JSON」，它仍然会给出：

```
```json
{"score": 8, "reason": "正确"}
```
```

或者「好的，我的评分如下：{...}」，或者把分数写成字符串 `"8"`。

解析器（`src/lib/eval/parse-judge.ts`）处理了 5 种畸变，单独写了 16 个用例测。其中一半是**必须抛异常**的用例 —— 因为抛不抛这件事本身有业务含义：

**解析不出来 = 没测出来，不是 0 分。** 如果退化成 0，两个版本的分数差就可能是「这次 judge 恰好没按格式回」造出来的，而页面上看起来和「真的答得差」一模一样。

同理，判分失败在结果表里显示「失败」而不是 `0`。这和 Stage 0 定下的「失败也记录」是同一条原则的两面：**记录失败，但别把失败当成成绩**。

### 4. 一条用例一个请求

整批塞进一个请求最省事，但 Vercel 函数 60 秒就掐。30 条用例 × 2 次模型调用，必定超时 —— 而且超时之后**既不知道跑到哪，也拿不到已经花了钱的那些结果**。

拆成「一条用例一个请求」之后：

- 每条跑完立刻落库，断了能接着跑
- 客户端串行循环，进度条能显示「第 3/20 条」，随时可以停
- 幂等靠 `@@unique([evalRunId, caseId])`：重复请求直接返回已有的，不重复花钱

**为什么用数据库唯一约束而不是先查一下有没有**：前端并发点击时，两个请求可能同时通过「查一下」这个检查。检查和使用之间有窗口，这种 bug 在本地几乎复现不出来，上线后偶发。唯一约束是唯一真正原子的兜底 —— 插入冲突时捕获 `P2002` 再读回来就行。

### 5. Next 16 的 Cache Components：`params` 写在 Suspense 外面会挡住预渲染

`npm run build` 直接失败：

```
Route "/evals/[id]": Next.js encountered uncached or runtime data during prerendering.
```

原因是我把 `await params` 写在了页面组件的最外层。官方的意思是：**跟 URL 参数无关的外壳（页头、页脚）可以先发出去**，动态部分流式补。所以正确写法是把 `params` / `searchParams` 这两个 Promise **原样传进 `<Suspense>` 内部**再 await。

改完之后构建产物里 `/evals/[id]` 标的是 `◐ Partial Prerender`，和首页一致。

> 这和 W42 那条 `export const dynamic` 报错是同一个东西的另一面：框架不是不让你做动态页，是要求你**指出哪部分是静态的**。想清楚之后体验确实更好。

### 6. ESLint 拦住 `setState` 写在 effect 里 —— 它是对的

进度条需要「跑完 N 条之后重置」。第一版写成：

```tsx
useEffect(() => { setProcessed(0) }, [done])
```

`react-hooks/set-state-in-effect` 报错。一开始以为它死板，想加注释关掉。想了一下它说的其实对：`processed` 和 `done` 是**同一个数字的两种表示**，存两份就得手动同步，refresh 之后忘了清就会算成「6/3」。

改成在点击时直接维护**绝对进度**（`current` / `start`），`done` 变化时不需要任何同步代码。少一个 effect，也少一类 bug。

### 7. Windows 上 `prisma generate` 报 EPERM：dev server 锁住了引擎 DLL

跑完迁移后 `prisma generate` 失败：

```
EPERM: operation not permitted, rename '...query_engine-windows.dll.node.tmp30084' -> '...query_engine-windows.dll.node'
```

不是权限问题，是**文件被占用** —— 还开着的 dev server 进程已经把这个 DLL 加载进内存了。停掉它就行。

顺带又踩了一次 Git Bash 的老坑：`taskkill /PID 1234` 里的 `/PID` 被当成路径转换成了 `C:/Users/.../PortableGit/PID`。要加 `MSYS_NO_PATHCONV=1`。

**排查顺序值得记**：先按端口找 PID（`netstat -ano`），再看 PID 的**命令行**确认它确实是本项目的进程，最后才杀。按进程名杀 node 是危险的 —— 机器上可能还跑着别的东西。

### 8. 演示数据跑出了真实的差异（这次不是我设计的）

本来只是想让线上有点内容，结果那套题真的分出了高低：

| 版本 | 均分 | 关键差异 |
|---|---|---|
| v1-直接作答 | **8.0** | 利润题答成 1650（正确 1500），judge 给 0 分 |
| v2-分步计算 | **10.0** | 5 题全对 |

v1 的提示词是「直接给出最终答案，不要写计算过程」。模型真的就**心算**了 —— 120 件 × 35 元成本、90 件按 50 元、30 件打八折，它在脑子里算错了 150 元。

这印证了 W42 第 19 条（`calculate` 工具存在的理由）：**LLM 是在猜下一个 token，不是在做算术**。当时以为那只影响 agent，现在看它在普通问答里一模一样 —— 区别只是 agent 里你可以给它一个计算器，而「只比较 prompt」的评测里，你能做的就是把「先写步骤」写进提示词。

这也是评测平台存在的意义：**如果没有 judge 打分，这条 1650 会安安静静地混在「看起来都对」的回答里。**

### 9. 校验要放在录入时，不是调用时

测试失败路径时，我随手写了个不存在的模型名 `this-model-does-not-exist`。结果报错发生在**真花钱调用**的时候，而且整批评测每条都要失败一次才知道错在哪。

改成建 `PromptVersion` 时就校验模型名（对 `provider.models` 查一遍）。**同一个错误，早报比晚报便宜得多** —— 这跟 TypeScript 比运行时错误好在哪，是同一件事。

## 已知欠账

- **历史列表仍是一次扫 300 条 span 再分组**（W42 就记了）。数据量上来后要按 `runId` 分页。
- **`query_spans` 会查到当前正在跑的运行**。做 agent 评测时要决定是否排除自己。
- **思考模式的 token 仍没单独存**。
- **评测不支持重跑已完成的用例**。想重跑得新建一次评测 —— 这样是对的（历史不可变），但界面上没解释清楚。
- **每条例用串行跑，20 条要一两分钟**。想做并发得先解决「并发下怎么显示进度、怎么算钱」。
